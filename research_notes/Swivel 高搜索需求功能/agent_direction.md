## 1. Landscape (2025 – Oct 2026): what desktop assistants/agents advertise, how they act on the computer, user numbers, failure modes

### Takeaway
Every major vendor shipped a desktop agent in 2026 and they have converged on the same architecture: structured connectors/MCP/tools first, a browser second, pixel-level GUI control (Screen Recording + Accessibility on Mac) as the last resort, increasingly run in an isolated space (VM, agent workspace, virtual desktop, background windows) with per-app approvals. GUI control is still described by its makers as "early", slow and failure-prone, prompt injection remains unsolved, and the biggest 2026 safety incident (OpenClaw) came from a local agent's skill marketplace and default network exposure — while Microsoft is visibly retreating from pushing AI into OS menus after user backlash.

### Inferences
- The competitive bar for a *general* "operate my computer" agent is now set by Anthropic, OpenAI, Perplexity, Manus, ByteDance and Alibaba, all with frontier models, VMs/virtual desktops and large teams. A single-developer menu-bar app cannot win that head-on; Swivel's realistic edge is (a) native, deterministic, previewable local tools that agents and users can call, (b) zero/low-permission operation, (c) model routing that works for mainland-China users (where Claude, OpenAI and Gemini are unavailable and Apple Intelligence is not yet live — see §2), and (d) the Mac-specific "fix my computer" niche that none of the big agents markets.
- "Connectors first, GUI last" is now an explicit industry design rule (Anthropic quote; Codex plugins; Windows MCP connectors). Swivel's existing tools are exactly the kind of precise connector these agents prefer — exposing them via MCP and App Intents puts Swivel inside every agent rather than competing with them.
- Reliability: even ~85% OSWorld-Verified implies roughly 1 in 7 multi-step GUI tasks fail in benchmark conditions; vendors still say "early" and "may need a second attempt". GUI control should not run destructive or irreversible steps unattended.
- Isolation is the trend (Cowork VM, Windows agent workspace + agent account, Doubao virtual desktop, background-window control). macOS gives third parties no equivalent of Windows' agent account; Swivel would have to approximate isolation by restricting itself to files the user explicitly hands over, its own output folders, and per-app approvals.
- Microsoft's File Explorer retreat is a direct warning for Swivel's drag menus: AI entries injected everywhere annoy users; Swivel's existing "each tool off by default, switch on individually" model is the right posture for agent features too.
- OpenClaw's failures map to concrete rules for Swivel: no third-party skill marketplace (or signed, reviewed bundles only), bind any local server to 127.0.0.1 (prefer stdio), never accept tokens or endpoints via URL parameters, and treat installation instructions inside skills/content as untrusted.

## 2. Model options for Swivel: Apple Foundation Models (on-device and PCC), cloud APIs via URLSession, local runtimes

### Takeaway
On macOS 26 the only built-in model is Apple's ~3B on-device model with a 4K-token window (tool calling and @Generable guided generation included), usable only where Apple Intelligence is on — which excludes mainland China today (a limited China rollout is *reported* for December via iOS 27.3, Mac unconfirmed). macOS 27 (shipped Sep 2026) adds image input, a rebuilt on-device model, a 32K-context PCC server model (free but only for App Store Small Business Program developers under 2M lifetime downloads), and — most important for Swivel — a public `LanguageModel` protocol so any HTTP model (Claude, Gemini, or a home-grown OpenAI-compatible conformer for DeepSeek/Qwen/Kimi/GLM/Ollama) can drive the same `LanguageModelSession`, tools and @Generable types. For Swivel's audience the practical stack is: on-device Apple model where available for cheap intent parsing, BYO-key cloud models (China-reachable ones first) via URLSession for reasoning, and an optional local Ollama/LM Studio backend.

## 4. Permissions for an agent that sees and operates other apps on macOS, how competitors stage consent, and safety patterns

### Takeaway
Seeing and driving other apps on macOS requires **Screen Recording** (ScreenCaptureKit) + **Accessibility** (AXUIElement / synthetic input); both Claude and OpenAI ask for exactly those two, then layer their own per-app approvals, blocked categories, confirmation before sensitive actions, and "can't approve system privacy prompts / can't drive Terminal" rules. Screen Recording consent was made recurring (monthly) in macOS 15 with no developer opt-out, Accessibility control is incompatible with the App Sandbox/Mac App Store, and prompt injection remains unsolved (best published browser-agent rate ~11% before newer mitigations). The safe pattern is a staged permission ladder with read-only and file-scoped tools first, explicit per-app/per-action consent, previews, undo logs, and treating all screen/web/file content as data.

### Cited Findings
- [Doc] OpenAI computer use: Screen Recording "so ChatGPT can see the target app", Accessibility "so it can click, type, and navigate"; app approvals are separate from macOS permissions; "can't automate terminal apps or ChatGPT itself"; cannot authenticate as admin or approve security/privacy prompts; asks before sensitive/disruptive actions; admin app restrictions; locked-screen mode needs an Apple **authorization plug-in** and relocks on local input — [ChatGPT docs](https://learn.chatgpt.com/docs/computer-use.md); [heise](https://heise.de/-11306153)

### Inferences
- **Permission ladder for Swivel (each rung its own switch, off by default):**
  - *Rung 0 (today, no TCC):* tools act only on files the user drags/picks or an MCP host passes; read-only diagnostics via fixed commands (§5); model calls via URLSession; App Intents; MCP stdio.
  - *Rung 1 (user-selected screen content, ideally no Screen Recording):* "look at this window" through `SCContentSharingPicker` or the screenshot card Swivel already receives from Clothesline; OCR + model explanation. Read-only.
  - *Rung 2 (Automation / Apple Events, per target app):* scripted actions on specific apps (Finder reveal/tag, Music, Mail draft) — macOS asks once per target app; still no blanket control.
  - *Rung 3 (Accessibility + Screen Recording):* full GUI control, explicitly labelled experimental, per-app allowlist like Codex ("ask" / "always allow"), hard-blocked apps (Terminal/iTerm, System Settings Privacy panes, password managers, banking/payment, Swivel itself), visible "agent is acting" overlay with a stop key, pause on user input like Claude, and expect the monthly Screen Recording re-consent.
  - *Rung 4 (privileged fixes):* never executed silently; show the exact command and why, let the user run it in Terminal or approve an admin prompt; Full Disk Access and Input Monitoring avoided entirely.
- **Action-risk classes**: read-only (auto), reversible local writes beside originals (auto with undo log), moves/renames/deletes-to-Trash (preview + confirm), anything sending/publishing/purchasing/changing settings (confirm every time, never "always allow"), irreversible deletes or credential entry (refuse; hand to user).
- **Prompt-injection posture**: OCR text, screen content, web pages, file contents and diagnostic output are *data*; they must never expand permissions or trigger confirm-class actions without a fresh user confirmation shown with the model's stated reason. Keep the "lethal trifecta" separated: a session that reads untrusted content should not simultaneously hold network-send + private-data tools without a human gate.
- Mac App Store distribution and Rung 3 are mutually exclusive (sandbox); staying Developer-ID/ad-hoc keeps Rung 3 possible but forfeits PCC eligibility (§2).
- The macOS 15 monthly Screen Recording prompt makes always-on screen watching (Highlight-style) a poor fit for a utility that promises "no permissions"; on-demand capture of a user-picked window fits Swivel's ethos better.

## 5. "Problem-solving" agent patterns: read-only diagnostics, grounded answers, consented escalation

### Takeaway
Shipping "fix my computer" assistants are narrow and conservative: Microsoft's Settings agent maps language to a fixed catalog of settings functions on a tiny on-device model and acts with permission; Apple's AI support assistant answers and escalates to humans with heavy disclaimers; MacPaw's Moonlock/Eney turn settings into guidance and ask before acting; Raycast/Codex let models run shell commands under approval. macOS already ships every diagnostic CLI a Mac-doctor agent needs, so Swivel can offer a curated, read-only diagnostic toolset with model-written explanations and user-confirmed, reversible fixes — a niche none of the big general agents markets.

### Inferences
- **"Mac doctor" design**: a catalog of named, parameter-checked diagnostic tools (not a free-form shell): disk space (`du` on user folders, `diskutil info /`, `tmutil listlocalsnapshots /`), battery/sleep (`pmset -g batt`, `pmset -g assertions`, `system_profiler SPPowerDataType`), network (`networkQuality`, `scutil --dns`, `networksetup -getinfo Wi-Fi`, `ping`/`dig`), Spotlight (`mdutil -s /`), login/background items (`launchctl list` for the user domain), security posture (`spctl --status`, `csrutil status`, `fdesetup status`), crash/hang reports (`~/Library/Logs/DiagnosticReports`), recent errors (`log show --last 1h --predicate …` with tight predicates). Outputs are summarized locally first (byte caps, redaction of serials/usernames/SSIDs) before any cloud call; the model explains and proposes; fixes are separate, confirm-class actions (open the right System Settings pane, move caches to Trash with undo, rebuild Spotlight only after confirmation, or show the admin command for the user to run).
- **Grounding**: answers should cite where possible (Apple Support article URLs via the model's web search tool when using Claude/Qwen with search, or a small bundled knowledge list); Apple's own assistant shows that disclaimers + escalation paths are expected.
- **Staged roadmap implied by §§1–5** (for the report writer): (1) App Intents + MCP server for existing tools (no model, no permission); (2) natural-language Quick Actions using on-device FM where available, BYO-key cloud otherwise (DeepSeek/Qwen default for China, Claude/OpenAI elsewhere), with @Generable plans and previews; (3) read-only Mac-doctor diagnostics + explanations; (4) user-picked-window understanding (`SCContentSharingPicker` / screenshot card) for "what is this error dialog?"; (5) opt-in Automation/Accessibility GUI actions with per-app approvals, only after 1–4 prove value. Model choice per stage: on-device for parsing, cheap cloud (Haiku 5.5 / DeepSeek flash) for diagnostics summaries, frontier (Sonnet/Opus 5.5, Qwen3.8-Max) only for GUI control or hard reasoning.
- Several diagnostics (`powermetrics`, some `log` scopes, `sfltool dumpbtm`) likely need administrator rights — treat them as Rung 4 and exclude from the default catalog until verified.
